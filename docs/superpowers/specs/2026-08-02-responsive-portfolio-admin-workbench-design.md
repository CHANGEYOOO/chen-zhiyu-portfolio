# 响应式作品管理工作台设计规范

日期：2026-08-02  
状态：设计方向已确认，等待书面规范复核

## 1. 项目判断

当前管理页已接入 Cloudflare Access、D1、R2 与 Worker API，但界面仍沿用旧版“作品列表 + 弹窗表单”结构。它能够承载基本字段，却没有把本地文件选择、分片上传、上传恢复、图片排序、草稿、预览、发布和异常处理组织成清楚的工作流程。

本轮重设计的任务不是让后台更像前台作品集，而是建立一个可靠、清晰、在电脑与手机上都能完整工作的内容生产工具。视觉应延续网站的暖黑、暖灰、直角和编辑字幕语气，但任何电影化表达都不得降低上传、排序和发布效率。

## 2. 目标

- 电脑端和手机端都能从本地选择并上传图片与视频；
- 只管理前台作品区已经使用的文字和媒体字段；
- TVC 与 Livestream 拥有各自清楚、无多余字段的编辑流程；
- 大视频分片上传可暂停、继续、失败重试，并能在刷新或短暂断网后恢复；
- Livestream 图片数量不设业务上限，每张图片可预览、上传和排序；
- 文字保存、媒体上传和作品发布相互独立，避免一次失败清空全部进度；
- 所有不可逆或影响线上展示的动作都有清楚的状态与确认；
- 保持现有 Cloudflare 架构、字段模型和前台回退逻辑不变。

## 3. 非目标

- 不管理 About、Contact、首页首屏或第二屏视频；
- 不增加网络媒体地址输入；所有新媒体只能来自本地文件；
- 不提供公开注册、多人协作、评论、审批流或角色系统；
- 不增加自动视频转码、自动剪辑或 AI 生成内容；
- 不提供 D1 记录或 R2 对象的物理删除；第一阶段只归档；
- 不迁移到 React、Vue 或其他框架；继续使用原生 HTML、CSS 和 JavaScript；
- 不重构与本轮管理界面无关的前台视觉或 Worker 数据模型。

## 4. 体验原则

### 4.1 工作流优先

界面先回答三个问题：正在编辑哪件作品、哪些内容尚未保存、哪些文件仍在上传。装饰、动画和品牌表达不得抢占这些信息。

### 4.2 保存与上传分离

文字字段可以立即保存为草稿；媒体文件进入独立上传队列。上传失败不回滚已保存文字，也不要求成功文件重新上传。

### 4.3 移动端不是缩小版桌面端

桌面端采用并列工作区；移动端采用列表页与全屏编辑页的顺序流程。两端功能一致，但布局和操作密度分别适配鼠标、键盘和触摸。

### 4.4 线上状态始终可见

草稿、已发布、已归档、未保存、上传中、上传失败和版本冲突必须使用文字说明，不只依赖颜色或图标。

### 4.5 安全发布

“保存草稿”和“发布”是两个明确动作。发布前必须完成字段与媒体完整性检查，归档、取消发布和覆盖冲突必须要求确认。

## 5. 信息架构

后台由四个稳定区域组成：

1. 顶部状态栏；
2. 作品浏览与筛选；
3. 作品编辑器；
4. 全局上传队列。

### 5.1 顶部状态栏

显示：

- `CHEN ZHIYU / WORKS ADMIN`；
- 当前网络状态；
- 当前管理员邮箱；
- 正在上传的文件数量；
- 返回网站；
- 退出登录。

移动端只保留品牌标识、网络／上传状态和更多菜单，避免顶栏拥挤。

### 5.2 作品浏览与筛选

提供：

- 全部、TVC、Livestream 栏目筛选；
- 全部状态、草稿、已发布、已归档状态筛选；
- 按品牌名、作品名或直播名搜索；
- 新增 TVC、新增 Livestream 两个明确入口；
- 作品数量与筛选结果数量；
- 作品级排序模式与“保存排序”；
- 上传活动与未保存修改提示。

作品条目显示：

- 封面缩略图；
- 品牌名与影片名，或直播名；
- 作品类型；
- 栏目；
- 状态；
- 最近更新时间；
- 媒体完整性摘要；
- 编辑、复制、取消发布／发布、归档／恢复操作。

移动端的次要操作收进条目内的操作菜单，编辑是整行主要动作。

### 5.3 作品编辑器

编辑器不再使用居中弹窗。

桌面端：

- 左侧作品列表保持可见；
- 右侧为宽度受控的独立编辑工作区；
- 媒体较多时编辑区内部滚动，顶部身份与底部保存栏保持可见；
- 可返回列表而不关闭上传队列。

移动端：

- 从列表进入全屏编辑页；
- 顶部提供返回与作品状态；
- 内容按“基本信息—媒体—排序与预览—发布”顺序排列；
- 底部固定操作栏提供保存草稿、预览和发布；
- 软键盘出现时操作栏不得遮挡输入框。

编辑器采用四个可定位段落，不使用多层弹窗：

1. 基本信息；
2. 媒体；
3. 排序与前台预览；
4. 发布状态。

## 6. 核心流程

### 6.1 新增 TVC

1. 点击“新增 TVC”，立即在浏览器生成稳定 work id；
2. 填写品牌名、影片名和作品类型；
3. 保存草稿，文字数据可以先写入 D1；
4. 从本地选择 Poster，显示裁切预览、文件名、大小和处理状态；
5. 浏览器生成 desktop 与 mobile WebP，失败时保留原文件并提供重试；
6. 从本地选择视频，加入分片上传队列；
7. 上传期间可以继续编辑文字、离开作品或切换至其他作品；
8. 所需媒体完成后启用发布前检查；
9. 预览确认后发布；
10. 发布成功后列表状态与前台公开数据同步更新。

### 6.2 新增 Livestream

1. 点击“新增 Livestream”，生成稳定 work id；
2. 填写直播名和类型并保存草稿；
3. 从本地一次或多次选择任意数量图片；
4. 每张图片成为独立上传项目，成功与失败互不影响；
5. 图片卡显示缩略图、文件名、大小和上传状态；
6. 通过拖动或上移／下移调整顺序；
7. 第一张始终标记为“前台封面”；
8. 排序变化只在点击“保存图片排序”后写入 D1；
9. 预览确认后发布。

### 6.3 编辑已发布作品

- 打开已发布作品时，页面显示“当前线上版本”；
- 修改文字或媒体后进入“有未发布修改”状态；
- 保存草稿不得自动覆盖前台展示；
- 重新发布前显示本次变更摘要；
- 版本冲突时停止覆盖，提供“重新载入线上版本”和“复制当前内容为新草稿”；
- 第一阶段不实现强制覆盖。

### 6.4 取消发布、归档与恢复

- 取消发布：作品回到草稿，前台停止返回；媒体保留；
- 归档：作品从默认列表和前台隐藏，媒体保留；
- 恢复：作品回到草稿，不直接重新发布；
- 所有操作使用确认面板说明影响，不使用浏览器原生 `alert` 或 `confirm`；
- 不提供物理删除按钮。

## 7. 上传系统设计

### 7.1 全局上传队列

上传队列独立于编辑器存在，并按作品分组。顶部状态栏显示活动数量；点击后展开底部抽屉或移动端全屏队列。

每个文件显示：

- 缩略图或媒体类型标记；
- 文件名和大小；
- 所属作品；
- 已上传／总大小；
- 百分比与进度条；
- 等待、处理中、上传中、已暂停、失败、已完成、已取消状态；
- 暂停、继续、重试和取消操作。

### 7.2 图片上传

- 允许 JPEG、PNG、WebP，单文件上限沿用 Worker 规则；
- 选择后立即生成本地预览；
- 图片并发数量受控，防止手机内存和网络被占满；
- 单张失败只重试该文件；
- 页面离开或刷新前保存待上传与已完成状态。

### 7.3 视频分片上传

- 所有 TVC 视频使用 R2 multipart；
- 分片大小与并发数沿用现有 API 规则；
- 暂停停止派发新分片，不丢弃已经完成的分片；
- 继续时先从 Worker 获取已完成分片再补传；
- 网络断开时自动进入“等待网络”；恢复后允许自动继续或手动继续；
- 刷新后通过本地草稿中的 upload id、object key 与 part 清单恢复；
- 若浏览器因系统限制失去本地文件访问权限，明确要求用户重新选择同一文件，并通过名称、大小和内容指纹校验后继续；
- 不承诺网页在 iOS 被系统彻底关闭后继续后台传输，但重新打开页面后应恢复可继续状态。

### 7.4 离开页面保护

存在未保存文字、待上传文件或活动上传时：

- 页面内导航先显示自定义离开提示；
- 浏览器关闭／刷新使用 `beforeunload` 作为最后保护；
- 已保存文字和已完成分片不丢失；
- 提示必须区分“未保存文字”和“未完成上传”。

## 8. 表单与媒体组件

### 8.1 基本信息

TVC：

- 品牌名；
- 影片名；
- 作品类型。

Livestream：

- 直播名；
- 类型。

栏目一经创建后不允许直接互换，避免媒体结构与字段失配。若选错栏目，创建新的正确草稿并归档错误草稿。

### 8.2 本地文件选择器

- 整块区域可点击，电脑端支持拖入文件；
- 手机端明确显示“从设备选择”；
- 选择后显示本地预览，不上传即不离开设备；
- 不显示网络 URL 字段；
- 文件类型和大小错误在选择后立即反馈。

### 8.3 Livestream 图片排序

- 桌面端支持拖动；
- 手机端支持长按拖动；
- 两端都保留上移和下移作为可靠替代；
- 排序期间禁止同时保存同一作品的另一套顺序；
- 未保存排序使用清楚的边框、文字和固定操作栏提示；
- 保存成功后更新服务器基准顺序并清除脏状态。

### 8.4 前台预览

- 预览使用现有前台作品卡样式和裁切逻辑；
- TVC 显示 Poster、品牌名、影片名和作品类型；
- Livestream 显示第一张封面、直播名、类型与完整图片顺序；
- 预览不得要求作品已发布；
- 移动端预览覆盖 390px 级别布局；
- 预览只读，不在预览层直接编辑。

## 9. 状态模型

### 9.1 作品状态

- `draft`：后台可编辑，前台不可见；
- `published`：前台可见；
- `archived`：默认隐藏，前台不可见；
- `dirty`：客户端有尚未保存的文字或排序；
- `publishing`：正在执行发布校验与提交；
- `conflict`：服务器版本高于当前编辑版本。

`dirty`、`publishing` 和 `conflict` 是界面状态，不改变 D1 的三种持久状态。

### 9.2 上传状态

- `ready`；
- `processing`；
- `uploading`；
- `paused`；
- `waiting-network`；
- `failed`；
- `complete`；
- `cancelled`。

界面状态必须与 UploadManager 的可恢复数据一致，避免只改视觉标签而没有真实行为。

## 10. 错误、空状态与反馈

### 10.1 错误原则

- 错误靠近发生位置显示，同时在全局状态区提供摘要；
- 文案说明发生了什么、哪些内容已保留、下一步可以做什么；
- 不使用“未知错误”“Oops”或只显示状态码；
- 技术详情可折叠，默认不打扰正常操作。

### 10.2 必须覆盖的错误

- Access 登录过期；
- 设备离线；
- API 请求失败；
- 不支持的文件类型或超限；
- 图片处理失败；
- 单次图片上传失败；
- multipart 创建、分片、完成或取消失败；
- 文件重新选择不匹配；
- D1 版本冲突；
- 发布前字段或媒体不完整；
- 图片排序保存失败。

### 10.3 空状态

- 无作品：说明可以新增 TVC 或 Livestream；
- 筛选无结果：保留清除筛选入口；
- 无上传：说明选择本地文件后队列会显示进度；
- Livestream 无图片：显示上传入口与“第一张将作为封面”；
- 已归档为空：不使用鼓励归档的营销文案。

## 11. 视觉规范

### 11.1 视觉定位

后台是与作品网站同一品牌下的“内容剪辑台”，不是对前台电影页面的复制。电影感只体现在秩序、比例、文字层级和克制的状态变化中。

### 11.2 色彩

- 页面背景：暖调近黑；
- 工作区表面：略亮炭灰；
- 主文字：柔和灰白；
- 次级文字：暖烟灰；
- 唯一强调色：低饱和钨丝灯暖棕；
- 错误色：低饱和砖红；
- 成功、警告和状态不能只靠色彩区分。

### 11.3 字体与数字

- 中文操作与正文使用系统无衬线字体，确保手机可读性；
- 英文品牌与小标签延续现有大写字距，但不把所有操作写成全大写；
- 文件大小、百分比、排序和时间启用等宽数字；
- 页面只保留一个主标题层级，不使用超大作品集式 Hero；
- 正文最小字号不低于 14px，辅助信息不低于 12px。

### 11.4 形状与层级

- 工作区、输入框、媒体卡和按钮保持直角或极小圆角；
- 不使用通用白底阴影卡片；
- 分区主要依靠间距、底色和细线；
- 关键操作使用实心按钮，次要操作使用文字或边框按钮；
- 危险操作不与保存按钮并排争夺注意力。

### 11.5 动效

- 只使用 160–240ms 的状态过渡；
- 上传进度使用真实进度，不伪造缓动进度；
- 列表与编辑器切换使用轻微位移和透明度；
- 排序使用位置变换，不改变图片比例；
- 支持 `prefers-reduced-motion`；
- 不使用入场电影转场、滚动叙事或持续装饰动画。

## 12. 响应式规则

### 12.1 桌面端

- 视口宽度大于等于 1024px 时使用列表／编辑器并列布局；
- 作品列表建议占 34%–40%，编辑器占剩余宽度；
- 最大内容宽度约 1440px；
- 上传队列使用右下或底部抽屉，不覆盖保存操作；
- 鼠标拖放是增强功能，所有动作仍可通过按钮完成。

### 12.2 平板与手机

- 小于 1024px 改为列表页与编辑页顺序导航；
- 不保留挤压后的双栏；
- 所有触摸目标至少 44×44px；
- 固定底栏考虑 `env(safe-area-inset-bottom)`；
- 文件选择、上传队列、排序、预览和发布均可在触摸环境完成；
- 图片列表优先单列或稳定双列，不使用自动瀑布流；
- 横屏手机仍采用移动流程，不强制切换桌面双栏。

## 13. 可访问性

- 提供跳到主内容链接；
- 页面区域使用 `header`、`nav`、`main`、`section`、`article` 和 `aside`；
- 当前筛选、当前作品、上传状态和保存反馈具有可读语义；
- 拖拽排序提供键盘与按钮替代；
- 进度条使用 `role="progressbar"` 和实时数值；
- 状态更新使用节制的 `aria-live`，避免每个上传字节都朗读；
- 焦点在列表、编辑器、确认面板和预览之间按操作来源返回；
- 所有文字、输入与按钮满足 WCAG AA 对比度；
- 不依赖悬停显示唯一信息。

## 14. 技术边界与组件职责

继续使用现有模块边界，并按职责补充，不把全部状态继续堆进 `admin.js`。

- `admin.js`：页面编排、路由状态与跨组件协调；
- `api-client.js`：Cloudflare API 请求、错误标准化和版本参数；
- `draft-store.js`：表单草稿、恢复元数据和离开保护；
- `upload-manager.js`：队列、并发、暂停、继续、网络恢复和 multipart 状态；
- `sortable-list.js`：作品和图片排序；
- `media-attachment.js`：上传完成结果转为作品媒体关联；
- 新增视图模块：作品列表、编辑器、上传队列、确认面板和预览；
- CSS 按页面骨架、组件、状态与响应式组织，继续使用原生 CSS 变量。

不得把 Access token、R2 凭据、D1 凭据或 Worker secret 写入浏览器代码。管理 API 继续校验 Cloudflare Access JWT 和管理员邮箱。

## 15. 数据流

1. 页面启动后请求 `/api/admin/session`；
2. 认证成功后请求作品列表；
3. 选择作品时加载服务器版本与本地草稿；
4. 表单变更写入本地草稿并标记 dirty；
5. 保存草稿通过版本号更新 D1；
6. 文件选择进入 UploadManager；
7. 上传完成后通过媒体关联 API 写入 object key；
8. 图片顺序单独保存；
9. 预览从当前表单、已上传媒体和本地预览组合生成；
10. 发布前重新获取服务器版本并执行完整性校验；
11. 发布后刷新当前作品、列表和公开缓存；
12. API 失败时保留本地草稿与上传恢复信息。

## 16. 验收标准

### 16.1 桌面与手机共同验收

- 未授权用户无法访问管理数据；
- 授权邮箱可以进入后台；
- 可以从本地文件完成一次 TVC 新增：文字、Poster、视频、草稿、预览和发布；
- 可以从本地文件完成一次 Livestream 新增，图片数量任意；
- Livestream 第一张图片作为封面，顺序保存前后行为明确；
- TVC 视频显示真实分片进度，并支持暂停、继续和单次失败重试；
- 网络短暂断开后，表单、成功文件和已完成分片不会丢失；
- 页面刷新后能恢复草稿和可继续上传状态；
- 手机端可完成文件选择、图片排序、上传、预览和发布；
- 已发布作品的修改不会在仅保存草稿时自动影响前台；
- 发布前检查可以阻止缺少必要媒体或文字的作品；
- 草稿与归档作品不出现在公开 API；
- 不存在网络地址输入或物理删除入口。

### 16.2 状态与异常验收

- 所有状态都有文字标签；
- 登录过期、离线、API 失败、文件不匹配、上传失败、排序失败和版本冲突均有可恢复路径；
- 离开含未保存修改或活动上传的页面会得到准确提示；
- 空列表、筛选无结果、无上传和无图片都有明确空状态；
- 不使用浏览器原生 `alert` 或 `confirm`。

### 16.3 视觉与可访问性验收

- 后台延续暖黑、暖灰、直角和低饱和暖棕视觉系统；
- 不再使用超大 Hero 或居中弹窗作为主要工作结构；
- 1024px 以上为并列工作区，小于 1024px 为顺序全屏流程；
- 390×844 视口无横向溢出、遮挡或小于 44px 的主要触摸目标；
- 键盘可以完成筛选、编辑、排序、保存、预览和发布；
- 减少动效模式下不影响任何功能。

### 16.4 回归验收

- 现有 Cloudflare Access、D1、R2 与 Worker API 继续工作；
- 现有 30 个 TVC、8 个 Livestream 及媒体顺序不被修改；
- 公开作品 API、静态回退和视频 Range 播放不受影响；
- 现有管理 API 与上传测试继续通过；
- HTML、CSS、JavaScript 静态检查和 `git diff --check` 通过；
- 完成桌面与真实移动视口的浏览器复核。

## 17. 发布与回滚边界

- 本轮先在 `codex/cinematic-v2` 工作树中实现和验证；
- 未经用户确认，不把管理页发布到生产；
- 保留当前已部署 Worker 版本、D1 数据、R2 对象和 Supabase 回退；
- 视觉重设计出现问题时可回退管理页静态文件，不回滚数据库或媒体；
- 任何 D1、R2 或 Supabase 物理删除仍需新的明确授权。
